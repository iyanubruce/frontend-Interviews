# Front End System Design: An Introduction

> Source: [introduction](https://www.greatfrontend.com/front-end-system-design-playbook/introduction)

Unlike coding and quiz questions, system design interviews are open-ended style interviews where there are no right answers. Candidates are given a vague problem or scenario and they are expected to work with the interviewer to answer the question by coming up with a suitable software design on a whiteboard, or in the case of virtual interviews, a collaborative drawing app like Excalidraw.

In many ways, system design interviews are similar to the process at certain companies where engineers write technical design documents to outline the possible approaches to a project they are working on, explain technical decisions, and discuss tradeoffs with coworkers except that time is limited (around 30-60 minutes).

System design interviews are usually asked to candidates who have some number of years of working experience (aka non-fresh grads) and their performance in the system design interview has significant influence on the job level and salary offered.

> **System design performance drives both the hire decision and the level**
>
> For senior and beyond, a weak system design round almost always results in an overall rejection, and even a passing score here is what separates senior from staff offers. Treat it with the same weight as coding, not as a secondary round.

Given the open-ended nature of system design interviews, it is much harder to practice for it as compared to coding interviews. Many candidates also don't have real life experience building various systems and it's hard to draw from experience when answering system design interview questions. Also, there are very few resources available for front end system design. Most existing system design resources are targeted at general Software Engineers and hence focus on distributed systems.

GreatFrontEnd aims to fill the gap with this Front End System Design Playbook. This guide covers a framework, evaluation criteria, common mistakes, and worked front end system design examples.

## Front end vs Back end / Full stack system design

In traditional Software Engineer system design interviews, candidates are asked to describe the architecture of a distributed system, usually involving cloud infrastructure, web servers, API gateways, load balancers, caches, databases, microservices, message queues, streams, etc.

Front end system design interviews are slightly different – there's more emphasis on what goes on in the client and the API details between clients and servers, as opposed to what goes on in the back end.

| Aspect                                    | Back end / Full stack                                                                                                                      | Front end                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Gather requirements                       | Required                                                                                                                                   | Required                                                                                     |
| Architecture / High-level entities        | Distributed cloud services (e.g. Load balancer, Application server, Database, File storage, Caches, Message queues, CDN, Full-text search) | Components within the client (View, Store, Networking layer)                                 |
| Back-of-the-envelope capacity estimation  | May be required                                                                                                                            | Usually not required                                                                         |
| Data model                                | Database schema                                                                                                                            | Application state                                                                            |
| Less important (Can treat as a black box) | Client                                                                                                                                     | Server                                                                                       |
| Type of APIs between components           | Between distributed services (HTTP, gRPC, etc.)                                                                                            | Between server and client (HTTP, WebSocket), Events / actions between client-side components |
| Deep dives / focus areas                  | Scalability, Reliability, Consistency, Availability                                                                                        | Performance, User Experience, Accessibility, Internationalization                            |

For example, a classic question is to "Design the Facebook news feed". This question can be asked in both back end and front end system interviews, but the focus is entirely different:

- **Back end / full stack system design**: Capacity estimation, designing the database schema, APIs between microservices, scaling services for high traffic, how to generate a user's news feed in a scalable fashion, what happens when a post is created by a typical user (hundreds of followers) vs celebrities (millions of followers)
- **Front end system design**: HTTP API to fetch the feed, implementing feed pagination, implementing interactions with posts (liking, commenting), how users can create new posts, performance, user experience, and accessibility considerations

Focus on client rendering, state, APIs, performance, and accessibility.

> **Generic system design resources will mislead your preparation**
>
> Most existing material is written for back end interviews and centers distributed systems, capacity planning, and database sharding, topics rarely evaluated here. Use guides written for front end interviews so you spend prep time on rendering, state, API shape, performance, and accessibility instead.

## Exercises

### Check your understanding 1

Which concerns are characteristic of a front end system design interview? Select all that apply.

- [x] Define the view, store, networking layer, and application state on the client.
  > This is front end-focused because the architecture is decomposed inside the browser rather than across cloud services.
- [x] Design the HTTP or WebSocket contracts used by the client and discuss rendering, accessibility, and UX.
  > These are front end concerns because they determine how the client obtains data and presents an effective interface.
- [ ] Choose database shards and replicas for millions of writes per second.
  > This is a back end concern because front end interviews usually treat the server and database internals as a black box.
- [ ] Estimate the number of application servers and message queues required at peak traffic.
  > This is typical back end capacity planning rather than client-side architecture and behavior.

### Check your understanding 2

For a front end “Design a news feed” interview, which scope is most appropriate?

- [x] Cover the feed API, pagination, post interactions and creation, client state, performance, UX, and accessibility.
  > This is best because it addresses how the browser retrieves, stores, renders, and updates the feed experience.
- [ ] Focus on fan-out strategies for ordinary users versus celebrities and the microservices that generate feeds.
  > This is primarily back end scope because it concerns distributed feed generation behind the client API.
- [ ] Spend the session normalizing every database table and omit the client application.
  > This misses the front end assessment because database schemas are not the application state and UI architecture being evaluated.
- [ ] Draw the final screen and omit data flow, API behavior, state, and interactions.
  > This is incomplete because front end system design evaluates a working client architecture, not only visual appearance.

### Check your understanding 3

Which preparation choices align with the guide's recommended front end system design focus? Select all that apply.

- [x] Work through application and component case studies such as a news feed and autocomplete.
  > These cases build transferable experience with the two main front end system design question categories.
- [x] Practice reasoning about performance, UX, accessibility, internationalization, state, and API boundaries.
  > These are the front end deep-dive areas that distinguish the discipline from distributed back end design.
- [ ] Prepare exclusively with resources centered on load balancers, sharding, and distributed queues.
  > This miscalibrates preparation because generic system design material emphasizes topics rarely evaluated in front end rounds.
- [ ] Prioritize every other round because system design has little effect on leveling.
  > This is risky because system design performance strongly influences both hiring and level for experienced candidates.
